## 優先 0:品質基礎(最優先)

**目標**:改出問題時,在合併之前就被自動抓到,不再靠使用者親自使用才發現。

**現況**:

- `tests/` 有 95 個檔案:25 支 `.sh` 驗收腳本(其中 18 支用假資料模式,7 支需要真正的 CLI)、6 支單元測試,其餘是畫面腳本和輔助程式。
- 沒有 CI。每支腳本的執行方式不同,要手動逐一執行,也沒有統一的結果。
- 這一輪開發暴露的問題:
  - **測試只驗證「有沒有做」,沒驗證「效果對不對」。** 例如合成語音念錯字、角色的聲音其實沒播出來,測試都沒抓到。
  - **舊測試悄悄過時。** 例如 `media` 測試還在檢查 2a 之前的朗讀行為,`claude-content.test.mjs` 不帶參數就會失敗。
  - **版本號一直是 0.1.0。** 安裝檔分不出新舊,也沒有更新紀錄。

**工作項目**:

1. **統一的測試入口**:
   - `npm test`:單元測試,用 node 直接跑,幾秒內完成。
   - `npm run test:e2e`:假資料模式的驗收腳本,逐一執行並彙整「通過 / 不符」。
   - `npm run test:real`:需要真正 CLI 的腳本,會花額度,只在手動執行時跑。
   - 每支腳本都要輸出一致的結果格式(例如最後一行「全部通過(N 項)」或「有 N 項不符」),讓入口程式能判斷成敗。
2. **GitHub Actions(Windows)**:每個 PR 和每次推送到 `main` 時,自動跑型別檢查、建置、`npm test` 和主要的假資料驗收腳本。失敗就擋下合併。
3. **「驗證效果」的測試原則**,寫進 `docs/安裝與測試.md`,新功能都要照做:
   - 會產生內容的功能,要檢查內容本身。例如語音合成要用語音辨識確認念對;摘要要檢查念出來的字。
   - 有退回機制的功能,要分別驗證「成功路徑真的成功」和「失敗時有退回」。例如音訊要確認真的開始播放,而不是只確認嘗試過。
   - 改了行為,就要同時改測試的預期,不能讓舊預期留著。
4. **整理現有測試**:逐一跑過所有假資料腳本,修好過時的預期;刪掉或合併重複的腳本;每支腳本開頭寫清楚它驗證什麼。
5. **版本與更新紀錄**:
   - 採用語意化版本,下一版是 0.2.0(語音模式、總管、角色聲音)。
   - 新增 `CHANGELOG.md`,每次發布列出新功能、修正和已知問題。
   - 用 git tag 和 GitHub Releases 發布安裝檔。
6. **PR 範本**:列出「跑過哪些測試」「有沒有更新文件」「有沒有更新測試預期」的檢查項目。

**完成標準**:

- 開 PR 時,GitHub Actions 自動跑完並顯示結果;任何一項假資料驗收腳本不符,PR 就無法合併。
- `npm test` 和 `npm run test:e2e` 在乾淨的環境都能直接執行並全部通過。
- 發布 0.2.0,附上更新紀錄。

**已決定**(2026-11-20):CI 分兩組:每次 PR 跑型別檢查、建置、單元測試和幾支核心驗收腳本;完整的假資料驗收腳本**每週跑一次**。

**進度**(2026-11-21,PR #3,分支 `feat/ui-fixes-and-roadmap`):

- ✅ 統一測試入口 `tools/run-tests.mjs`:`npm test`(單元 10 支)、`test:core`(7 支,每次 PR)、`test:e2e`(21 支,每週,含版面檢查)、`test:local`(語音服務 3 支)、`test:real`(真正的 CLI 7 支)。

## 優先 1:總體儀表

**進度**:✅ 已實作(2026-11-21),還沒發布;說明見[功能說明](功能說明.md)的「總覽儀表」。「另外」那一項(總管預設用每次詢問)還沒做。

**目標**:一眼看到整體狀況:各家額度還剩多少、今天花了多少、有幾個節點在跑或在等你,超過預算會提醒或擋下。

**做法**:把右側上方的「節點清單」**完全拿掉**,換成「總覽」儀表(2026-11-20 決定)。節點本身在主面板上已經看得到;清單原本負責的兩件事要另外安置:「需要你的節點排最上面」併入儀表的狀態區(點一下跳到該節點),「外部觀察節點」移到儀表裡的一個區塊或「遠端」面板。

**儀表內容**:

1. **額度**:三家後台各自的額度視窗(例如每 5 小時、每週),用進度條顯示已用百分比和重置時間。資料已經有:`BackendUsage`。
2. **花費**:今天、本週的 token 數和金額,依後台和節點分開。資料來源是 `agent.spent` 和 `TaskInfo.cost`;需要新增「依日期彙總」的紀錄,才能算出今天和本週。
3. **狀態**:執行中、排隊中、等你處理(授權或提問)、異常的節點數;點一下跳到對應的節點。
4. **預算**(新功能):單位是**額度百分比**(2026-11-20 決定)。以**每週額度**為準:每日預算預設是週額度的 1/7(約 14%),可以自己調整;今天週額度增加的百分比超過預算時**只提醒、不擋**(擋下新指令仍由現有的「額度上限」負責)。
5. **提醒**:額度快滿、預算快用完、節點異常太久。

**完成標準**:

- 儀表的數字和各家 CLI 回報的一致。
- 每日預算超過時會提醒並說明用量;實際阻擋仍由「額度上限」負責。
- 有驗收腳本:用假資料模式驗證數字、提醒和預算阻擋。

**已決定**(2026-11-20):
- 每日預算以每週額度計算(預設 1/7,可調),超過只提醒。每天第一次讀到的週額度百分比當作起點,今天的用量 = 目前讀數 − 起點;週額度在當天重置時,起點歸零重新累計。
- 儀表**常駐**在右上角:平常顯示精簡版(各後台的額度條與狀態數字:執行中、等你處理、排隊、異常),點一下展開完整內容(花費、今天的任務數、外部觀察節點、預算設定)。

**另外**:總管預設用「每次詢問」模式,並在新增總管時提醒自動模式的風險。

## 優先 2:總管與協作

**進度**:⬜ 還沒寫程式。2-1 長期記憶的設計已定案(見[記憶設計討論](記憶設計討論.md)),預定放進 0.3.0。總管節點、總管守則、會議與節點互相呼叫已經有了。

### 2-1 主控台自己的長期記憶

**目標**:總管和節點能記住跨對話的事,例如哪個節點擅長什麼、這個專案的慣例、你的偏好、過去分派的結果,讓分派越用越準。

**為什麼要「自己的」**:各家 CLI 的記憶彼此不相通,也不知道其他節點的存在。主控台是唯一看得到所有節點和所有結果的地方,記憶應該放在這裡,並且讓三家 agent 都能用。

**設計**(2026-11-21 定案,完整內容見[記憶設計討論](記憶設計討論.md)):

- **儲存**:記憶庫是一個 Markdown 資料夾 `<資料目錄>\memory-vault\`,每筆記憶一個檔案(YAML 屬性 + 內文);主控台在資料庫建索引,並偵測外部修改。
- **管理在另一個 app**:主控台只讓 agent 讀寫(`memory_search`、`memory_write`),沒有管理畫面;使用者用**完全獨立的記憶庫管理 app**(自己的安裝檔,圖書館風格,功能待討論)管理同一個資料夾。
- **範圍**:混合式(節點側寫、偏好是全域;專案知識、判例依專案);專案用 git 共用目錄認定,任務的專案在交辦當下寫入。
- **節點側寫是工作履歷**:基本資料、特長(總管寫)、任務紀錄(自動;完成率與驗收率分開)、解決問題的流程。總管守則附上約 1500 字的精簡版。
- **解法紀錄(判例庫)**:困難任務的候選由承辦節點直接撰寫成獨立的案件檔;客觀欄位由主控台自動填、先標「未確認」、每天設上限。
- **刪除節點時**歸檔進記憶庫(可先請節點寫工作總結,可略過),新增同名節點時可以接回。
- **隱私**:記憶預設送給總管;送出前遮罩金鑰、密碼。
- **分階段**:資料與統計 → 側寫與工具 → 判例庫 → 刪除節點的歸檔 → 記憶庫管理 app。

### 2-2 可重複使用的協作流程

**目標**:常用的協作模式做成一鍵套用,不用每次用話交代。

- 例如「A 實作 → B 審查 → A 依意見修改 → C 寫測試」「三個節點各自提案 → 開會收斂」。
- **流程定義**:放在資料夾裡的設定檔,指定步驟、每步交給誰(或交給「最適合的節點」由總管挑)、要傳給下一步的內容。
- **執行方式**:由主控台的流程執行器負責,做法類似現在的會議主持;或交給總管照流程分派。
- **介面**:在總管或節點上選一個流程,填入主題就開始;每一步的進度和結果都看得到。

### 2-3 協作過程可視化

- **主面板上的連線**:節點之間有交辦(`ask_node`)或會議進行中時,在面板上畫出連線和方向。
- **分派紀錄**:總管交辦了什麼給誰、花了多少、結果如何,可以回頭查看。
- **任務面板**:被交辦的任務標示來源,例如「由總管交辦」。

### 2-4 總管的預設建議

- **模型**:實測(`tests/chief-real.sh`)Claude Sonnet 最快、回覆最簡潔,當作預設建議;Gemini 可以用 Hydrogen;不建議 Orchestrator。
- **權限**:預設「每次詢問」,每次分派前先確認。

## 優先 3:語音模式定位

**進度**:✅ **2026-11-20 結案**。語音輸入、語音播報、角色聲音(CosyVoice)、語音引擎層、固定語音與手動卸載都已完成。下面標 🔶、⬜ 的項目移到「之後再說」,不排進目前的任務清單。

**方向**:語音輸入和語音播報已經好用。「每個角色有自己的聲音」很有特色,但安裝成本高(要 10 GB 以上的環境),台灣口音也還沒有完美解法。所以:

- **系統語音是預設**,不用安裝任何東西就能用語音播報。
- **角色聲音是進階選項**,語音引擎可以切換。

**工作項目**:

1. **語音引擎抽象化**(✅ 第一步完成):主控台的引擎層在 `src/main/speech.ts`,「語音」面板的「播報的聲音來源」可以勾選和排順序,依序嘗試、都沒有聲音時用系統語音。
   - 已有:**固定語音**(角色資料夾 `clips\` 預先錄好的短句,依事件播放,不需要語音服務)、**本機語音合成**(CosyVoice)。
   - ✅ 本機語音合成可以手動卸載與載入,實測顯示卡記憶體 2642 MB → 40 MB。
   - ✅ 固定語音已用 ElevenLabs 錄製的 claude 角色實測播放成功;另外兩個角色的台詞稿已寫好。
   - 🔶 雲端引擎(ElevenLabs API):研究完成(端點、中文模型 `eleven_flash_v2_5`、免費額度與授權限制),等使用者的免費金鑰實測「免費方案能不能用 API、自建聲音能不能透過 API 使用、每個中文字扣多少額度」,再決定要不要做。注意免費不能商用、播報摘要會送到 ElevenLabs。
   - ⬜ BreezyVoice 引擎;完成時「固定語音加摘要」的組合播法。
   - ⬜ 語音辨識模型還沒下載完整時,畫面只顯示「模型載入中」,應改成顯示下載進度。
2. **BreezyVoice 優化**:實測它的台灣口音最自然,但一句要 25 到 29 秒。優化方向:
   - 用「只取聲紋」的模式:實測一句 2 到 8 秒。
   - 把參考聲音的特徵快取起來,多音字元件常駐,不要每句都重開。
   - 修好它的子行程做完不會自己結束的問題。
   - **目標**:一句 5 秒以內。做得到的話,設為台灣使用者的預設引擎。
3. **發音修正字典**:常念錯的詞(例如 BreezyVoice 的「流程」、節點的英文名字)可以設定注音或讀音,所有引擎共用。
4. **遠端語音(Phase 4)**:之後再排。
