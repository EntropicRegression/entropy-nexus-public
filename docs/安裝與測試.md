# 安裝、執行與測試

> 目前只在 Windows 上開發與測試。

## 需求

- Windows 10 或 11
- Node.js 22 以上
- 至少安裝並登入一家 CLI:[Claude Code](https://claude.com/claude-code)、Codex,或 Antigravity(`agy`)。沒有安裝的那幾家會顯示成不可用。
- 遠端操作需要 [Tailscale](https://tailscale.com/)(選用)

## 執行

```bash
npm install
npm run dev        # 開發模式
npm run build      # 建置到 out/
npm start          # 執行建置後的版本
npm run typecheck
npm run dist       # 打包成 Windows 安裝檔,輸出到 release/
```

安裝檔沒有程式碼簽章,第一次執行時 Windows SmartScreen 會警告。

不想動用額度時,設定 `NEXUS_FAKE=1` 可以讓三家都改用假資料轉接器,方便看畫面與開發。資料存在 `%APPDATA%\entropy-nexus`;設定 `NEXUS_DATA_DIR` 可以改放到別處。其他環境變數見[功能說明](功能說明.md)最後一節。

## 測試

測試用統一的入口 `tools/run-tests.mjs` 執行,依組別分成:

| 指令 | 內容 | 時間 | 什麼時候跑 |
|---|---|---|---|
| `npm test` | 單元測試,用 node 直接跑,不需要建置 | 幾秒 | 每次修改;CI 每次 PR |
| `npm run test:core` | 核心的假資料驗收腳本:互相呼叫、會議、總管、語音播報、佇列 | 約 6 分鐘 | CI 每次 PR |
| `npm run test:e2e` | 全部假資料驗收腳本 | 約 25 分鐘 | CI 每週一次 |
| `npm run test:local` | 需要本機 Python 與語音模型(語音辨識、語音合成) | 約 5 分鐘 | 改到語音服務時手動跑 |
| `npm run test:real` | 需要真正的 CLI,**會花額度** | 依腳本而定 | 改到轉接器時手動跑 |

- 驗收腳本跑的是建置後的 `out/`,所以除了 `npm test`,其他組別都會先自動建置(加 `--no-build` 可以略過)。
- 只跑其中幾支:`node tools/run-tests.mjs e2e --only interop,meeting`;看有哪些:`node tools/run-tests.mjs e2e --list`。
- 每支測試的完整輸出存在系統暫存區的 `nexus-test-runs\<組別-時間>\`,結果另存成 `summary.json`。
- 驗收腳本也可以單獨執行,例如 `bash tests/interop.sh`(用 Git Bash)。
- 假資料模式不碰 `%APPDATA%\entropy-nexus` 的正式資料,也不花額度。

CI(GitHub Actions,Windows):`.github/workflows/ci.yml` 在每次 PR 和推送到 `main` 時跑型別檢查、`npm test` 和 `npm run test:core`;`.github/workflows/weekly.yml` 每週跑一次 `npm run test:e2e`,也可以在 Actions 頁面手動執行。

### 寫測試的原則:驗證效果,不只驗證「有做」

這個專案曾經發生過:測試全部通過,但合成語音其實念錯字、角色的聲音其實沒播出來,都是靠實際使用才發現。所以新功能的測試要照下面的原則寫:

1. **會產生內容的功能,要檢查內容本身。** 例如語音合成要用語音辨識確認念對;語音摘要要檢查實際念出的文字;排版要檢查產生的結構(例如表格真的變成 `<table>`)。
2. **有退回機制的功能,成功和失敗兩條路都要驗。** 例如播放合成語音要確認音訊真的開始播放(`playing` 事件),而不是只確認「嘗試播放」;另外再驗證失敗時有退回系統語音。
3. **改了行為,就同時改測試的預期。** 不能讓舊的預期留著,不然測試會在下一次全面執行時才失敗,或更糟,一直通過卻沒有在測任何東西。
4. **輸出要讓測試入口判斷得出成敗。** 每項檢查印出「通過」或「不符」,最後一行印「全部通過(N 項)」或「有 N 項不符」。結束代碼不是 0、或輸出有「不符」「失敗」「等不到」,都會被判定為失敗;什麼都沒印也算失敗。
5. **新的驗收腳本要登記在 `tools/run-tests.mjs` 的清單裡**,並放進正確的組別;執行快、涵蓋核心流程的才放進 `core`。

## 專案結構

- `src/main/`:主行程。核心服務、事件資料庫、各家 CLI 的轉接器(`adapters/`)、遠端服務、節點互相呼叫的工具服務。
- `src/preload/`:畫面可以呼叫的固定函式。
- `src/renderer/`:畫面(React 與 PixiJS)。
- `src/shared/`:主行程與畫面共用的型別。
- `tests/`:驗收腳本。
