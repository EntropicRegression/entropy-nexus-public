# 可重用的協作流程(發展規劃 2-2)規劃

**狀態**:已定案(2026-11-22,使用者三點都裁示「照建議」)。排程：完成任務清單 2-7 之後開工。

## 會議資訊

- **時間**:2026-11-22,開了 4 輪(上限 5 輪)。
- **主持**:claudia jr。
- **參與**:administrator、Hagemi、vault assistant、vault keeper。

## 原型

這幾天寶庫 App 各個里程碑的實際做法，就是這套流程的人工版：

1. vault keeper 實作。
2. claudia jr 做唯讀的獨立審查。
3. administrator 轉達意見、要求修正，再請 claudia jr 複審。
4. 使用者授權 commit。

整個過程有幾個痛點，第一版就是要解決它們:
- 管理員要自己重跑節點宣稱「通過」的測試。
- 範圍限制每次都要口頭重講，例如「只改 src/renderer、不要 commit」。
- 節點的回覆曾經遺失。
- 規格有歧義時，實作和審查兩邊會來回繞圈。
- 授權範圍散落在對話裡，不容易確認批准了什麼。

## 第一版(MVP)範圍

### 1. 定義與角色
- 流程用 YAML 定義：內建範本放在 repo,使用者自訂的放在主控台資料夾。
- 內建一條流程:**實作 → 隔離審查 → 修正 → 複審**。
- 角色由專案固定指定，例如這個專案的實作是 keeper、審查是 claudia jr。總管不負責挑人。
- 步驟欄位包括:`id`、`role`、`mode`(write / review)、`inputs`、`outputs`、`on_reject`、`requires_approval`。

### 2. 執行器
執行器由主控台內建，以狀態機運作。

**退回與停機**
- 審查有「必修」就退回實作者，最多退回 2 輪；第 3 輪還有必修，就停機交給使用者。
- 審查意見分三類:
  - **必修**:退回實作者。
  - **建議**:實作者自行判斷要不要改。
  - **需裁示**:直接交給使用者，不計入退回輪數。

**暫停與停止**
- 使用者隨時可以暫停或停止流程。
- 停止或改派之前，要先用交辦 ID 確認原本的交辦已經結束，避免兩個節點同時寫同一份工作區。
- 改派之後，舊交辦遲到的回報不能推進流程，也不能讓已停止的流程復活。

**修正步驟**
- 優先送回原本的實作 session。
- 原 session 已經不在時，才開新的交辦，並附上 `step_report`、必修清單和相對交審版本的 diff。
- 紀錄要標明這一步是延續原 session,還是開了新 session。

### 3. `step_report` 工具(新增的 MCP 工具)
節點要呼叫這個工具才算完成這一步，主控台不解析自由文字。

- 必填欄位依步驟類型而定，實作步驟看不到審查專用的欄位。
- 欄位:
  - `verdict`:可合併或需修正。主控台會檢查它和必修清單是否一致，有必修就不能填可合併。
  - `必修` / `建議` / `需裁示`。
  - `commands_run`:實際跑過的指令與結果。
  - `not_verified`:明確列出沒驗證到的事。
  - `questions`:要請使用者裁示的問題。
  - `scope_exceptions`:每改一個範圍外的檔案，都要寫一筆原因。
- 每份回報綁定流程、步驟、交辦 ID 和版本；同一個交辦重送時只記一次。
- 節點沒交回報時，先提醒一次；還是沒交，就記成**「未回報」**。
  - 「未回報」和核實失敗分開記錄，不計入退回輪數，也不退回實作者。
  - 會通知使用者，由使用者選「手動補報」或「重跑這一步」。

### 4. 版本(快照)
- 用獨立索引產生 git tree,**tree ID 就是版本**。它涵蓋未被忽略的新檔，也涵蓋刪掉的檔案。被 .gitignore 略過的產出要記下清單。
- 審查和核實都從同一個 tree 匯出副本。審查副本不含 `.git`,審查者碰不到正本，也碰不到 refs。
- 版本一變，舊的審查、核實和授權全部失效。
- 介面上標示為「**隔離審查**」,不宣稱是唯讀，因為 Codex 和 Antigravity 沒辦法硬擋寫入。
  - 審查結束後比對副本有沒有被寫入；有的話就標示並丟棄，絕不回寫正本。
  - 審查文件由主控台根據 `step_report` 代寫。

### 5. 核實
- 核實指令寫在流程定義裡，可以依專案覆寫。主控台自己重跑這些指令，不採信節點的自述。
- 第一版只跑文字指令(typecheck、單元測試、確定不開視窗的整合指令)。
  - 每條指令都要有逾時。逾時時終止這條指令啟動的子程序，並回報卡在哪一步。
  - 支援一層 `needs:` 依賴。前置指令失敗時，後面的指令標「略過(前置失敗)」,不再記成另一筆失敗。
- 結果分四類:

  | 結果 | 處理 |
  |---|---|
  | 通過 | 繼續下一步 |
  | 失敗 | 退回實作者 |
  | 被環境擋住 | 交給使用者，例如檔案被執行中的程式鎖住，並附上鎖定的程序；不計入退回輪數 |
  | 逾時 | 回報卡在哪一步 |

- 核實前後比較受版本控制檔案的**內容和清單**,確認核實指令沒有改到檔案。不用 `git status`,因為副本可能沒有 `.git`,而且同一個檔案被改寫兩次，狀態摘要可能看起來一樣。
- **需要桌面的核實**(例如會開視窗的 smoke):
  - 指令要標 `desktop: true`。
  - 只有專案設定勾了「允許桌面核實」才會跑，預設不勾。
  - 一定要帶逾時，而且在獨立 worktree 裡跑。
  - 沒跑的話，在 `not_verified` 寫「未跑桌面核實」。
  - 理由：寶庫的 CSP 問題就是靠 smoke 抓到的，typecheck 和單元測試當時全部通過。

### 6. 範圍合約
- 違反 `forbidden_actions`(commit、push、dist)時直接擋下。
- `allowed_paths` 用 tree 比對。改到範圍外只標示、不擋，交給審查者和使用者判斷，並搭配 `scope_exceptions` 的說明。改到範圍外的檔案，要使用者確認才會納入提交。
- 同一個工作樹，同時只允許一個流程寫入。

### 7. 授權卡
- 以下高風險動作一律要使用者確認，流程定義不能繞過:commit、push、碰真實記憶庫、安裝或覆蓋、合併 PR。
- 卡片上寫明這次授權涵蓋哪個版本(tree ID),以及**不涵蓋什麼**,例如「含本地 commit,不含 push」。
- 授權範圍記在流程實例裡，不散落在對話中。

### 8. 介面與紀錄
- 從任務面板的「套用流程」啟動：選範本、填主題和專案。
- 步驟條:
  - 用燈號顯示每一步的狀態：進行中、通過、被環境擋住、待授權、停機。
  - 點開可以看 `step_report` 的卡片和檔案連結。
  - 有停止鈕。
  - 不做視覺化編輯器。
- 每一步的產出都寫進主控台資料夾的 `runs/<id>/`,各有一份 json 和一份 md。下一步讀檔，不讀回覆，所以回覆遺失也能補回。

### 9. 總管
第一版的總管不負責挑人或分派。只有在流程停機或遇到「需裁示」時，總管才會收到通知，幫忙整理狀況。

### 10. 花費上限
用「輪數加時間」設上限，不用金額，因為各家後台的額度不同。

## 驗收

**假資料後台**
- 一次通過。
- 退回一輪後通過。
- 退回兩輪後停機。
- 「需裁示」不計入退回輪數。
- 「被環境擋住」不計入退回輪數。
- 「未回報」的處理。
- 遲到的回報不推進流程。
- 中途停止後不會復活。
- 審查通過後同一個檔案又被改動，版本失效。
- 原 session 不在了，改派新 session 後仍能完成。

**真實驗收**
- 寶庫 App 的一個小修正走完整條流程，由 vault keeper 實作、claudia jr 審查。
- 三家後台各至少做一次 `step_report` 回報，觀察它們是否確實遵守。

## 第二版

- 用 refs 暫存 commit 的完整快照。
- 開窗驗收預設開啟、更完整的桌面核實。
- 總管依側寫推薦或分派角色(要等側寫的特長夠可靠)。
- 「各自提案 → 開會收斂」流程(以現有的 `start_meeting` 為基礎)。
- 實作步驟也能在獨立 worktree 裡進行。

## 實作注意(會議中提出的陷阱)

- **worktree 搭配 `node_modules` junction**:清理時一定要先刪掉 junction 本身，再移除 worktree。直接 `worktree remove --force` 可能會循著連結，把真正的 `node_modules` 一起刪掉。這個清理順序由執行器負責。
- **只用 `git archive` 匯出 HEAD**:會漏掉新增和修改的檔案，所以改用獨立索引產生 tree。
- **`step_report` 靠節點自己願意呼叫工具**:真實驗收時要特別觀察各家後台的遵守率。
