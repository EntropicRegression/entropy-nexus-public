**依據**:[協作流程規劃](協作流程規劃.md)(使用者已定案)。

**來源**:2026-11-22 由規劃子代理只讀程式碼後擬定，claudia jr 整理。下文的「§N」指本文件的第 N 節。

## 2. YAML

- **解析**:一律用 `load(text, { schema: JSON_SCHEMA })`,不接受自訂型別，也不會執行任何東西。型別用一個本地的 `.d.ts` 宣告，不加 `@types/js-yaml`。
- **檔案位置**:
  - 內建範本:`src/main/flow/templates/`。
  - 使用者自訂:`<資料夾>/flows/*.yaml`。
  - 專案設定:`<資料夾>/flows/projects.yaml`,內容包含角色、核實覆寫、allowed_paths、允許桌面核實。
- **驗證規則**:
  - `id`(`^[a-z0-9-]+$`)、`name`、`steps` 必填。
  - 每一步要有 `role` 和 `mode`,`role` 必須出現在 `roles` 裡。
  - `on_reject` 要指向存在的步驟，或是 `halt`。
  - `next` 要指向存在的步驟，或是 `done`(流程通過、進入收尾的授權卡)、`halt`(停機)。省略時走定義順序的下一步，最後一步省略等於 `done`。
  - `needs` 只能一層，不能自己依賴自己。
  - 每條核實指令都必須有 `timeout`,上限 3600 秒。`desktop` 預設 `false`。
  - `forbidden_actions` 一律強制併入 `commit`、`push`、`dist`,以及永遠禁止的 `merge_pr`、`approve_pr`、`force_push`、`delete_branch`(§9 第 7 點)。
  - 高風險動作(`commit`、`push`、`real_vault`、`install`)只能透過 `requires_approval` 開放，也就是經授權卡同意後才能做，不能設成免授權。永遠禁止的動作連 `requires_approval` 也不能開放。
  - 不認得的欄位只記警告。
  - 專案覆寫用 `verify.mode: replace|append`;`append` 的 `needs` 可以指向範本裡的指令，合併後才檢查。
  - 專案設定可加 `verify_in: copy|worktree`(預設 `copy`,§9 第 6 點)。
  - `projects.yaml` 裡一個專案寫錯不影響其他專案；寫回時寫錯的專案原樣保留。

內建範本 `implement-review.yaml` 的草稿:

```yaml
id: implement-review
name: 實作 → 隔離審查 → 修正 → 複審
version: 1
description: 實作者寫完交審;審查者在隔離副本上審查;有必修就退回修正再複審。
roles:
  implementer: { mode: write,  description: 實作與修正 }
  reviewer:    { mode: review, description: 隔離審查與複審 }
limits:
  max_rejections: 2
  max_minutes: 180
  step_minutes: 45
  reminder_minutes: 10
  max_dispatches: 12
scope:
  allowed_paths: []
  forbidden_actions: [commit, push, dist]
verify:
  commands:
    - { id: typecheck, run: npm run typecheck, timeout: 300 }
    - { id: unit, run: npm test, timeout: 600, needs: [typecheck] }
steps:
  - { id: implement, label: 實作, role: implementer, mode: write, verify: true, on_reject: fix }
  - { id: review, label: 隔離審查, role: reviewer, mode: review, on_reject: fix, next: done }
  - { id: fix, label: 修正, role: implementer, mode: write, continue_session: true, verify: true, on_reject: fix, next: review }
finish:
  offer: [commit]
```

## 3. 狀態機

### 3.1 狀態與階段

- **流程狀態 `RunStatus`**:running、paused、awaiting_user(搭配一筆 `PendingDecision`)、halted、stopping、stopped、completed。
- **running 底下的階段**:dispatching → working → awaiting_report → snapshotting → verifying → exporting_copy → reviewing → post_review → finishing。
- **交辦 `Assignment`**:
  - 欄位:`id`、`stepId`、`attempt`、`agentId`、`sessionAtDispatch`、`sessionAtEnd`、`continuation`(continued、new)、`status`、`taskIds`、`queuedId`、`reminded`、`report`、`version`。
  - `status` 的值:queued、running、awaiting_report、reported、unreported、interrupted、superseded、failed、stopped。

### 3.2 規則

1. **回合結束才收尾**:收到回報先存起來，要等該回合結束(turn_ended)才收尾，因為節點可能還在寫檔。
2. **未回報**:回合結束時還沒有回報，就提醒一次；提醒後仍沒回報，交辦記成 unreported,進 `awaiting_user(unreported)`,讓使用者選「手動補報」或「重跑」。不計入輪數。
3. **輪數只計兩種**:審查的必修、核實失敗。
   - 需裁示、被環境擋住、逾時、未回報、節點出錯都不計入。
   - 退回超過 `max_rejections` 時停機(halted)。
4. **版本失效**:任何檢查點發現正本的 tree 不等於版本，該版本的審查、核實、授權全部失效，進 `awaiting_user(version_changed)`。
5. **停止或改派前先確認原交辦已結束(ensure_ended)**:
   - 交辦的 task 還在跑 → 中斷它，等到結束(30 秒逾時)。
   - 交辦還在佇列 → 取消佇列裡的那筆。
   - 節點正在做別人的 task → 不中斷。
6. **遲到回報**:交辦已經不是進行中時收到的回報，寫進 `late/`,不推進流程。流程如果正卡在未回報，這份回報只預填在手動補報欄位。
7. **終止狀態不復活**:流程已經是 stopped、completed 或 halted 時，任何事件都只記稽核紀錄、不處理。
8. **修正步驟的對象(chooseFixTarget)**:
   - 原節點的 session 沒變 → 送回原 session(continue),節點休眠就先喚醒。
   - 原節點的 session 換了 → 仍交給同一個節點，但算新 session(new)。
   - 原節點不在了 → 依專案的角色對照重新找節點，找不到就請使用者指定(need_user)。
   - 新 session 時，交辦要附上前一份 step_report、必修清單和 diff。
9. **持久化與重開**:
   - `run.json` 保存完整狀態，並記下啟動當時解析好的流程定義，執行中改 YAML 不影響。
   - 主控台重開後：執行中或停止中的流程改成 paused;進行中的交辦標成 interrupted;核實結果丟掉；殘留副本清掉。

## 4. step_report

- **參數**(英文):`assignment_id`、`summary`、`verdict`(mergeable、changes_required)、`must_fix`、`suggestions`、`needs_ruling`、`commands_run[{command,result}]`、`not_verified`、`questions`、`scope_exceptions[{path,reason}]`。
- **必填**:`assignment_id`、`summary`。
- **schema 寫法**:巢狀物件不寫 `required` 或 `additionalProperties`,因為現有 mcp-schema 測試會被截短。
- **驗證規則**:
  1. 交辦必須屬於呼叫者。
  2. 已有有效回報時，以第一次為準。驗證不過的回報不算數，節點可以修正後重送。
  3. write 步驟不接受審查欄位。
  4. review 步驟必填 verdict:mergeable 不能有必修,changes_required 必須有必修。
  5. 長度上限:summary 4000 字；每個項目 2000 字；每個清單 50 項。
  6. scope_exceptions 的路徑正規化成 repo 相對路徑，指到 repo 外面的拒收。
  7. 接受常見的參數別名。
- **單一工具**:MCP 的工具清單在 CLI 啟動時就固定了，沒辦法依步驟切換 schema。所以只用一個工具，交辦文字只列出這一步要填的欄位。

## 5. 版本、副本與核實

### 5.1 版本與副本

- **版本**:沿用 `snapshotTree`(暫存索引、`add -A`、`write-tree`)。
- **被忽略的產出**:用 `ls-files --others --ignored --exclude-standard --directory`,和 base 那份做差集。
- **匯出副本**:暫存索引 `read-tree` 之後 `checkout-index -a -f --prefix`,參數 `core.autocrlf=false`、`core.longpaths=true`。副本不含 `.git`,位元組和工作區一致。
- **副本被寫入的偵測**:用 `--git-dir=<repo> --work-tree=<copy>` 配暫存索引，再和版本 tree 比對。不碰 refs,也不靠 `git status`。
- **副本路徑**:`runs/<id>/copies/r-<tree8>`(審查用)、`v-<tree8>`(核實用)。
- **清理順序**:
  1. 先解除 junction。
  2. 確認已經沒有 reparse point。
  3. 再用 `rmSync` 刪除，重試 5 次。
  4. 失敗就留下來並記錄。
- **桌面核實的 worktree**:建立時用 `commit-tree`(不建 refs)加 `worktree add --detach`;清理時解除 junction → `worktree remove --force` → `prune`。
- **refs 指紋**:`for-each-ref` 加上 HEAD,用來偵測節點自己 commit 或 push。

### 5.2 核實

- **執行位置**:一般文字指令在 `v-` 副本裡跑，接上 node_modules。`desktop:true` 的指令只有專案勾了「允許桌面核實」才跑，而且在獨立 worktree 裡跑；沒跑就在 `not_verified` 寫「未跑桌面核實」。
- **啟動方式**:`spawn` 時 `shell: true`、`windowsHide: true`。
  - 環境變數要清掉 `NEXUS_*`、`ELECTRON_RUN_AS_NODE`,另外設 `CI=1`、`FORCE_COLOR=0`。
  - 輸出寫進 log,只保留最後 64KB。
- **逾時**:Windows 用 `taskkill /T /F`,posix 用 detached 加 `kill(-pid)`。記下卡在哪條指令和最後一行輸出。
- **結果分類**:
  - 結束代碼 0 → 通過。
  - 啟動失敗，或輸出出現 EBUSY、EPERM、被鎖、EADDRINUSE、ENOSPC、「不是內部或外部命令」等 → 被環境擋住，並找出鎖住檔案的程序。
  - 其他 → 失敗。
- **依賴**:前置指令沒通過時，後面的指令標「略過(前置失敗)」,不再記一筆失敗。
- **改檔偵測**:每條指令跑完都和版本 tree 比對，有差異就標示被改動的檔案。

## 6. 範圍合約與授權

- **forbidden_actions,分四層**:
  - **L1**:CLI 詢問授權時，摘要命中禁止動作 → 自動拒絕。
  - **L2**:工具啟動事件命中 → 中斷節點並停機。這一層盡力而為。
  - **L3**:~~啟動 CLI 時用 `GIT_CONFIG_*` 掛上 git hooks~~。使用者裁示第一版不做，改成每步前後比對 refs(§9 第 1 點)。
  - **L4**:事後比對 refs 和 `dist/`、`release/`。
- **allowed_paths**:用 `changedPaths` 加 `compileRules` 比對，只標示不擋。commit 時預設不納入範圍外的檔案，使用者在卡片上勾選的才納入。
- **工作樹鎖**:同一個工作樹，同時只允許一個流程寫入。
- **授權卡**:
  - 屬於流程層級，記在 `run.approvals`,不用 `core.requestApproval`。
  - 卡片寫明版本、涵蓋什麼、不涵蓋什麼。
  - 按允許時再拍一次快照，必須和卡片上的版本相同，才執行 `commitChanges(…, paths)`。

- **資料**:`Snapshot.flows`、`Update.flow`(單筆更新)、`FlowRunView`(步驟燈號、各次嘗試的回報與核實、待決事項、授權卡、違規紀錄)。
- **IPC**:`flowTemplates`、`flowProjectConfig`、`flowSetProjectConfig`、`flowStart`、`flowPause`、`flowResume`、`flowStop`、`flowDecide`、`flowManualReport`、`flowApprove`。只有完整權限的連線呼叫得到。
- **畫面**:任務面板的「套用流程」對話框、步驟條、授權卡與決策卡。

## 8. 測試

- **單元測試**:
  - `flow-def`:範本解析與驗證規則。
  - `flow-report`:回報的驗證與代寫的 md。
  - `flow-machine`:規格「驗收」的 10 條，外加暫停、時間上限、重開。
  - `flow-version`:用暫存 git repo 驗證 tree 涵蓋新檔與刪除、副本不含 `.git`、CRLF、寫入偵測，以及刪除副本後 junction 指向的目標仍然存在。
  - `flow-verify`:四類結果、前置失敗時略過、逾時連孫程序一起終止、改檔偵測。
  - `flow-scope`:glob 比對;`matchForbidden` 能抓到 `git -C x commit`、`git push`、`npm run dist`、`electron-builder`,而且不誤判 `git commit-tree`。
  - `mcp-schema`:補上 step_report 的檢查。
- **假資料 e2e**:`tests/flow.sh`,隔離方式照 meeting.sh,每個情境一個獨立的 git repo。fake.ts 的〔測試流程〕腳本可以控制假節點寫檔、回報、不回報、延後回報。e2e 情境對應規格「驗收」的 10 條。

## 9. 使用者裁示(2026-11-22)

1. **git hooks**:第一版不掛 L3 的 git hooks。改成事後偵測：每一步前後記錄 HEAD 與各 ref(含 `refs/remotes` 遠端追蹤分支、`refs/tags`),發現 commit 或 push 就標示違規、停機交給使用者。`forbidden_actions` 仍以工具層攔截為主。
   - M1:`version.ts` 的 `refsState` / `diffRefs` / `refsFingerprint` 涵蓋 HEAD 與 `for-each-ref` 的全部 refs。M2、M3 使用。
2. **核實指令改到受版本控制的檔案**:不算實作者失敗、不計退回輪數，交給使用者，並標明是哪個核實指令改了哪些檔。
   - M1:每條指令的結果記 `modified`;整組結果為 `modified`(不算 `fail`),`modifiedBy` 列出是哪些指令。
3. **「安裝或覆蓋」與「碰真實記憶庫」的範圍**:
   - 安裝或覆蓋：執行 `*Setup*.exe`、`.msi`(含 `msiexec`),寫入 `Program Files` 或 `%LOCALAPPDATA%\Programs`。
   - 碰真實記憶庫：寫入設定中的記憶庫路徑，或真實的 userData(`%APPDATA%\entropy-nexus`)。
   - 第一版以指令與路徑的 deny-list,加上核實時的環境隔離處理。
   - M1:`scope.ts` 的 `install`、`real_vault` 比對樣式照這個定義；記憶庫路徑是設定值，由呼叫端用 `protectedPaths` 傳入。核實時 `NEXUS_DATA_DIR` 指到臨時資料夾(核實結束刪除),被測的主控台用的是臨時 userData,碰不到真實資料夾與記憶庫設定；另外清掉 `NEXUS_*`、`ELECTRON_*`、`npm_*`、`INIT_CWD`、`GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE`、`NODE_OPTIONS`。
4. **總管收到停機或需裁示的通知**:只通知使用者並留言，不自動讓總管跑回合(M2)。
5. **時間上限**:扣掉暫停與等待使用者的時間(M2)。
6. **核實位置**:專案設定可選 `verify_in: copy`(預設)或 `worktree`;需要 git 的專案自己改成 `worktree`。
   - M1:`ProjectFlowConfig.verifyIn`,`applyProject` 寫進 `FlowDefinition.verify.in`;`runVerify` 依呼叫端給的位置執行，結果標明 `location`。
7. **永遠禁止**:合併 PR、核准 PR、force push、刪分支，與 commit、push、dist 同列，寫死在 `ALWAYS_FORBIDDEN`,流程定義不能開放。
   - M1:`merge_pr`、`approve_pr`、`force_push`、`delete_branch`;`scope.ts` 比對 `gh pr merge`、`gh pr review --approve`、`gh api …/merge`、`git push --force/-f/--force-with-lease/+refspec`、`git push … --delete/:branch`、`git branch -d/-D/--delete`。
8. **保護流程定義資料夾**:節點步驟的寫入範圍不得包含流程定義(`flows/`)與主控台設定資料夾(M3)。
   - M1:`scope.ts` 先提供 `protectedHits(paths, roots, base)` 判斷函式。
