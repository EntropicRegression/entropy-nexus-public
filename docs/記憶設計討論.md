# 長期記憶設計:討論資料

2026-11-21 整理,給「優先 2-1 主控台自己的長期記憶」開工前討論用。

## 目前的設計(2026-11-21 定案,第 2 版)

經過使用者決定、多節點會議評議(主持 administrator,評判哈gemi jr、gpt)與使用者裁示後的版本。這一節取代先前的「已決定」表;下方的「原始資料」保留當時的討論。

### 架構:記憶庫是一個 Markdown 資料夾

- **儲存**:記憶庫是固定的資料夾 `<資料目錄>\memory-vault\`,每筆記憶一個 `.md` 檔,開頭用 YAML 屬性記下種類、範圍、專案、來源、時間、確認狀態等欄位。
  - `memory-vault\nodes\`:節點側寫(工作履歷)與刪除節點時的歸檔
  - `memory-vault\cases\<專案>\`:解法紀錄(判例庫)
  - `memory-vault\knowledge\<專案>\`:專案知識
  - `memory-vault\preferences\`:使用者偏好
- **主控台只負責讀寫與索引**:agent 透過 MCP 工具 `memory_search`、`memory_write` 讀寫;主控台在資料庫建搜尋索引,並偵測檔案變動,外部修改後自動重新讀取。
- **使用者的管理在另一個 app**:主控台**沒有**記憶管理畫面。使用者用**完全獨立的「記憶庫管理 app」**(另一個程式、自己的安裝檔,主控台沒開也能用)開啟同一個資料夾,瀏覽、搜尋、編輯、刪除、確認判例。風格獨立於主控台,走**圖書館風格**;功能另外討論。(2026-11-21 決定;原本考慮的 Obsidian 因為自訂程度不夠而不採用。)判例的「參照先例」用 `[[案號]]` 連結,管理 app 可以直接點過去;Markdown 格式也保留了用一般編輯器臨時翻閱的可能。
- **衝突處理(2026-11-21 確認)**:agent 不覆寫使用者改過的檔案,只能新增或附加;以使用者的版本為準。2026-11-22 補充:
  - 附加時只附「和檔案目前內容相比有變動的章節」:依二級標題(`## `)比對,每一節和檔案裡同標題的最新版本(含之前的補充)比較,不同才附加;都沒變就不附加。格式仍是 `## 主控台補充(YYYY-MM-DD HH:mm)`(UTC),後面接有變動的 `## 章節`。
  - 附加前再比對一次檔案版本(mtime 與大小):讀取之後被別人(寶庫或使用者)改過,就重讀重算,最多 3 次,不蓋掉別人剛寫的內容。
  - 附加過的檔案一直算「使用者改過」,之後只附加、不再整份取代(原本附加後會重新登記,下一次寫入就整份取代,修正)。

### 範圍與專案

| 項目 | 決定 |
|---|---|
| 範圍 | **混合式**:節點側寫、使用者偏好是全域;專案知識、解法紀錄、分派紀錄依專案;查詢時拿「全域 + 目前專案」 |
| 專案認定 | git repo 用 `git rev-parse --git-common-dir` 對應到主 repo(同一個 repo 的 worktree 算同一個專案);不是 git repo 用**正規化後的工作目錄**(統一大小寫、斜線、去掉結尾斜線);monorepo 先當成一個專案 |
| 專案歸屬 | 任務的專案在**交辦當下**寫入(不要在重啟後用節點當下的工作目錄推算) |
| 「目前專案」 | 依被交辦節點的工作目錄判斷,不是總管自己的 |

### 記憶屬於誰

- 記憶**屬於節點**,不跟角色走:同一個角色給好幾個節點用時,各節點的側寫與判例各自獨立;節點刪除後由「歸檔」與「接回記憶」處理(2026-11-21 確認)。
- agent 查詢時,主控台依呼叫的節點排序結果(自己的側寫與判例在前);也可以指定節點查別人的。記憶庫管理 app 可以切換成某個節點的視角瀏覽(功能討論時再定)。

### 誰能寫

- **agent**:總管寫節點側寫的「特長」與專案知識;各節點寫自己承辦的判例(見下方)。**哪些節點能寫(2026-11-21 確認)**:所有節點都能讀;寫入如上。
- **使用者**:在記憶庫管理 app 裡管理(不經過主控台)。
- 寫入時**遮罩**看起來像金鑰、權杖、密碼的內容(取代成 `[已遮罩]`),而不是整筆拒絕。

### 總管怎麼用到

- 總管守則自動附上精簡的節點側寫與完成率,**約 1500 字**。分配規則:每個節點最多 3 行(特長一行、統計一行、最近的判例案號一行),依最近 30 天有任務的節點優先;超過字數時先截掉沒有近期任務的節點,最後附「另有 N 個節點,用 memory_search 查」。
- 需要更多時用 `memory_search` 查詢。

### 隱私(使用者裁示)

- 記憶**預設送給總管**(不論總管是哪一家),不額外提醒會送到哪一家,也不做「不提供給 agent」的標記。
- 送出前遮罩金鑰、密碼這類內容。

### 統計的含義(會議修正)

- 「完成」只代表回合正常結束;**使用者驗收**另外記錄(例如審查通過、使用者標記為完成、沒有被要求重做),完成率與驗收率分開顯示。
- 每筆記憶附上**最後確認的時間與當時的 commit**;太舊或專案已經大改的記憶,在查詢結果裡標示「可能過時」。

### 節點側寫:工作履歷

| 部分 | 內容 | 誰產生 |
|---|---|---|
| 基本資料 | 名稱、後台、模型、角色、做過哪些專案 | 主控台自動填 |
| 特長 | 擅長與不擅長的事 | 總管寫,交辦結束後隨時更新 |
| 任務紀錄 | 做過的任務標題、結果、耗時;完成率、驗收率與花費 | 主控台從任務資料自動整理 |
| 解決問題的流程 | 習慣的做法、常用的工具與步驟、成功的模式、常見的失誤 | 模型撰寫(見「刪除節點時」) |

### 刪除節點時:歸檔進記憶庫

- 側寫濃縮存進 `memory-vault\nodes\`(例如 `Hagemi-2026-11-21.md`)。
- 濃縮方式依序嘗試:
  1. 刪除前詢問「要先讓它寫工作總結再刪除嗎?」,**可以略過**;
  2. 節點已離線或略過:交給總管,依任務標題與各任務最後的回覆歸納;
  3. 都沒有:只存基本資料、特長、任務紀錄,「解決問題的流程」留空並註明原因。
- 新增節點時名稱或角色相同,提示「要接回某某的記憶嗎?」。

### 解法紀錄:判例庫(使用者採納折衷方案)

困難任務的最後解法寫成**獨立的案件文件**,像判決書與判例庫:每案有編號、格式固定、可以被引用。

- **觸發**:自動偵測到困難任務的候選時,**直接請承辦節點撰寫**;候選條件:耗時明顯比平常長(例如超過 30 分鐘)、中途失敗後才成功、審查被打回後修好、對話回合特別多。使用者也可以在任務面板對任何任務按「記下這個解法」。
- **三道保護**(回應會議裡「自己寫成績單、自我美化、花額度」的疑慮):
  1. **客觀欄位由主控台自動填**:任務 ID、專案 ID、來源、耗時、失敗次數、改過的檔案、承辦節點;節點只寫敘述的章節。
  2. **先標成「未確認」**:使用者在記憶庫管理 app 確認後,總管才查得到。
  3. **每天自動撰寫的份數設上限**(預設 3 份),控制額度。
- **存放**:`memory-vault\cases\<專案>\`,一案一檔,檔名是案號加案由,例如 `2026-0003-Electron視窗在測試中調不動大小.md`。案號全域連號(年份-流水號)。
- **格式**:

  ```
  ---
  案號: 2026-0003
  案由: 一句話描述問題
  專案: entropy nexus public
  承辦節點: Hagemi(Antigravity · gemini-…)
  任務: <任務 id>
  來源: 自動偵測 | 使用者標記
  耗時分鐘: 42
  失敗次數: 2
  改過的檔案: [src/main/index.ts, tests/layout.sh]
  commit: 4b91ec0
  狀態: 未確認 | 已確認 | 退回
  關鍵字: [electron, 視窗, 測試]
  ---
  # 解法第 2026-0003 號

  ## 事實經過        遇到什麼狀況、錯誤訊息或症狀
  ## 爭點            真正要解決的問題是什麼
  ## 處理經過        試過哪些方法,哪些沒用、為什麼(走過的彎路)
  ## 結論            最後有效的解法:改了哪些檔案、哪些設定、哪些指令
  ## 理由            為什麼這樣能解決(根本原因)
  ## 適用範圍        適用條件,什麼情況下不適用
  ## 參照先例        [[2026-0001]] 等相關案號(撰寫前先用 memory_search 查)
  ```

- **上限**:和專案知識**分開計算**。
- **用途**:總管交辦時查詢並附上案號與結論(「參照解法第 2026-0003 號」);撰寫新案時先列出相關先例;節點刪除後案件仍在。

### 專案知識

- 每個專案上限預設 50 筆;超過時請總管合併、去重,重新整理成較少的條目(使用者改過的檔案不動)。

### 分階段

1. **資料與統計**:記憶庫資料夾與索引、專案識別(交辦時寫入)、自動統計(完成率與驗收率分開)、總管守則附上節點統計。
2. **側寫與工具**:`memory_search`、`memory_write`、遮罩、總管寫側寫的特長、1500 字的分配規則。

4. **刪除節點的歸檔、接回記憶**。
5. **記憶庫管理 app**(獨立程式,圖書館風格):功能另外討論;等主控台開始寫入記憶(階段 2、3)後再做。

## 第二輪定案(2026-11-21,Hagemi 召開的兩場會議,使用者拍板)

### 記憶內容與工具

1. **對話草稿**:節點對話自上次儲存後累積超過門檻(預設約 3000 字,可調)時,對話視窗輸入列附近出現「儲存這段記憶」按鈕(不自動觸發);使用者按下後,請該節點把這段對話整理成草稿,寫入 `preferences` 或 `knowledge`,`狀態: 未確認`,使用者在管理 App 確認前 agent 查不到。按一次後按鈕消失,直到下一段再累積滿。
2. **分類**:「決策卡」「未完書籤」併入 `knowledge`,以 `子類: 決策` / `子類: 書籤` 區分(不開新資料夾);書籤另用 `狀態: 未完|已完成`,未完的在搜尋結果排前面。索引加 `subtype` 欄位,`memory_search` 可依子類篩選。新舊記憶的取代關係用 `取代: [[舊檔路徑]]`,搜尋預設隱藏被取代的那筆(舊檔不刪)。
3. **回顧**:各類記憶可在**檔案最後**加 `## 回顧`(兩三句,根據實際紀錄,不憑空編造)。多節點協作先由單一撰寫者統整並註明觀點出處;之後再加受限的 `memory_append`(只有參與者、只加在 `## 回顧` 下一行、每人一次)。
4. **`memory_read(path, include_review?)`**:回傳全文,預設不含 `## 回顧`;可見規則與搜尋相同。`memory_search` 計分與摘錄時也排除 `## 回顧`。
5. **熱度**:主控台在記憶庫根目錄維護 `.nexus-heat.json`(`{ 路徑: { 召回次數, 最後召回 } }`),記憶檔本身不動。
6. **召回**:只有呼叫 `memory_read` 才算一次召回;`memory_search` 的出現次數可另記但不算熱度。
7. **前幾行的版面**(已有共識):標題是一句可以單獨成立的話;判例在 `# 解法第 N 號` 下加一行 `摘要:<結論一句話>`;節點側寫的「特長」第一行寫最精華的一句(總管守則只取第一行前 80 字)。

### 與記憶管理 App 的對接

8. **圖像快照**:封存時把頭像與 `neutral` 立繪複製到 `nodes/封存/_圖像/<節點ID>/`(檔名改成 `avatar.<副檔名>`、`portrait.<副檔名>`,重複封存覆蓋),封存檔加 `頭像`、`立繪`(相對路徑)屬性。記憶庫裡 `_` 開頭的資料夾是附屬資料,索引與管理 App 都不當成記憶。
9. **欄位補充**:即時側寫補 `角色`;判例補 `參與節點ID: [..]`(主控台依會議紀錄與交辦紀錄自動填);封存檔補統計數字欄位(`任務數`、`完成數`、`完成率`、`驗收數`、`退回數`、`判例數`)與 `後台`、`sessionId`、`工作目錄`。
10. **`.nexus-stats.json`**(記憶庫根目錄):`更新時間`、`圖像目錄`、`節點`(每個節點ID:名稱、角色、狀態 線上|休眠|封存、統計、`專案`(名稱)與 `專案ID`(同序同長度的專案識別,2026-11-22 新增;同名不同專案的 ID 不同)、`頭像路徑`/`立繪路徑` 解析後的絕對路徑或 null、`session`:後台、sessionId、主控台有紀錄、CLI 有紀錄、工作目錄存在、可接回;可接回和喚醒網址同一個判斷,只有主控台資料庫的已終止節點才算,2026-11-22 修正)、`協作`(交辦:從、到、次數、最後時間,保留 30 天)、`同席`(會議)。最多每 5 秒寫一次、啟動時寫一次。2026-11-22 起另有 `專案表`、`總管任期`、`協作不含總管`、`同席不含總管`,節點另有 `專案任務數`、`總管`(見第四輪)。
11. **寫入方式**:`.nexus-heat.json`、`.nexus-stats.json` 都用「暫存檔 + 改名」原子寫入;Windows 上改名失敗(管理 App 正在讀)就短暫重試,仍失敗留到下一輪。管理 App 讀完立即關檔、忽略 `*.tmp`、解析失敗時保留上一份。
12. **跨 App 喚醒**:主控台註冊自訂網址 `entropy-nexus://wake?node=<節點ID>`;觸發時主控台(沒開就啟動)**一定先跳確認**,使用者同意後走既有的「開啟舊 session」復原同一個節點。不開本機 HTTP 端點。
13. **水晶合併規則**:同一個 `節點ID` 的多份封存合成同一顆水晶(「開啟舊 session」復原會沿用原節點ID);「新增節點時接回記憶」是新的節點ID,以 `接回自` 連成傳承線,不合併。

## 第三輪:管理 App 定案(2026-11-22,使用者裁示)

詳細設計在管理 App repo 的 `DESIGN.md`(v9 + 裁示)與 `docs/架構.md`;主控台這邊的摘要在 [視覺與互動規格](memory-vault-app/視覺與互動規格.md)。和主控台資料有關的部分:

1. **熱度名稱與門檻**:召回 0 次餘燼(`ember`)、1–2 次微溫(`tepid`)、3–4 次溫潤(`temperate`)、5 次以上炙熱(`flaming`);最後召回超過 30 天降一級。取代舊的「沉睡/餘溫/微溫/熾熱」與 0/1–2/3–6/7+。熱度由管理 App 從 `.nexus-heat.json` 的召回次數算,主控台只記次數與時間,`.nexus-heat.json` 格式不變。主控台畫面目前沒有顯示熱度名稱。
2. **四個書架**:判例(`cases/`)、決策(`knowledge` 的 `子類: 決策`)、書籤(`子類: 書籤`)、典藏(其餘專案知識 + `preferences/` 使用者偏好)。決策、書籤、典藏不編號,顯示「類別 · 日期」;判例用案號。節點側寫不上書架,只在樓上水晶履歷呈現。記憶檔的資料夾與欄位不因此改變。
3. **卡片頭像章**:承辦(`節點ID`)在前、`參與節點ID` 在後,最多 3 枚;圖像經管理 App 的 `vault-image://node/<節點ID>/avatar` 讀主控台提供的頭像(`.nexus-stats.json` 的 `頭像路徑`,或封存快照 `nodes/封存/_圖像/<節點ID>/avatar.*`)。
4. **水晶位置與光暈**:位置依節點 ID 決定式自動擺放;光暈依「經歷豐富度」分白/綠/藍/紫/金/紅六級,第七級彩虹只能由使用者手動頒發。計分用已確認判例(承辦/參與)、`驗收數`、`退回數`、`完成數`、跨專案數(建議值,細節仍可調);跨專案數用 `.nexus-stats.json` 的 `專案ID` 去重,舊資料沒有 `專案ID` 時退回用 `專案` 名稱。

## 第五輪:會議紀錄寫進記憶庫(2026-11-22,claudia jr 召開的短會,使用者裁示「照建議」)

**參與者**:vault keeper、vault assistant、Hagemi。

**使用者已決定**:
- 每場 `start_meeting` 結束時，主控台自動把逐字紀錄寫進記憶庫，狀態是「未確認」。
- 使用者確認後，總管和節點可以查到並引用。
- 主面板另有「會議室虛擬節點」,這是主控台內部的事，見任務清單 2-7。

會議定了以下格式。

### 1. 路徑
`meetings/<專案資料夾>/<YYYY-MM-DD>-<主題>.md`
- 專案資料夾的名稱沿用 `cases/<專案>/` 的規則(`safeName`),另外多兩條(2026-11-22 實作時補):
  - 去掉 `[ ] # ^ |`,避免弄壞 `[[...]]` 連結。
  - 去掉開頭的 `_` 和 `.`,因為記憶庫不掃描這種資料夾。

  所以專案名稱是 `_tools` 時，判例在 `cases/_tools/`,會議紀錄在 `meetings/tools/`。寶庫比對專案時應該以檔頭的 `專案ID` 為準，不要只看資料夾名稱。
- 主題先遮罩本機路徑，再轉成安全的檔名；同名時加序號。

### 2. 檔頭欄位
- `種類: 會議紀錄`、`主題`、`輪數`。
- `開始`、`結束`、`更新時間`:都用 ISO UTC。`更新時間` 等於結束時間，寶庫用它排序，不靠檔案的修改時間。
- `節點ID`(主持人)和 `主持人`(名稱)。
- `參與節點ID` 和 `參與者`:
  - **不含主持人**(2026-11-22 定案):主持人只寫在 `節點ID`/`主持人`;`參與節點ID` 只列被找來開會的節點，和 `start_meeting` 的 participants 一致。寶庫要列出「所有出席者」時，把兩者合起來。
  - 兩個清單同順序。
  - **檔頭的所有字串值一律用雙引號**(包含名稱、主題、專案、時間、狀態),跳脫 `\` 和 `"`。所以名稱裡的全形「，」「、」、半形逗號、`#`、冒號都在引號內，不能拿來切分清單；只有引號外的半形逗號才是清單分隔。`輪數` 是數字，不加引號。
  - 名稱是空字串時改寫節點 ID。
  - 寶庫只靠 ID 判斷是誰，名稱只用來顯示。
  - 兩個清單長度不一樣時，不按位置配對。
- `專案ID`、`專案`:格式和判例一樣，星系歸屬與專案篩選要用。
- `摘要`:結語的第一個非空段落;沒有結語時留空。
- `結束原因`:完成、中止或逾時。
- `產出`(2026-11-22 修正，原本寫的 `decisions/` 資料夾並不存在):
  - 決策草稿實際存放在 `knowledge/<專案>/<標題>.md`,檔頭是 `子類: 決策`(由主持人用 `memory_draft` 提交)。所以連結寫成 `產出: ["[[knowledge/<專案>/<標題>.md]]"]`(清單，可以有多份);決策那邊反向寫 `來源會議: "[[meetings/<專案>/<檔名>.md]]"`。
  - **第一版主控台不寫這兩個欄位**:散會時還沒有決策草稿，主控台也不自動產生決策。之後由主控台在主持人提交決策草稿時補上雙向連結(`memory_draft` 加一個指定來源會議的參數，排在之後的版本),主持人不必手動編輯檔案。
  - 寶庫要能處理沒有 `產出` 的會議紀錄(第一版一律沒有)。
- `狀態: 未確認`。

### 3. 逐字稿結構
- `## 結論`:放在最前面，有結語才寫。結語來自主持節點用 `meeting_say` 結束會議時附帶的文字;沒有結語就整節不寫，寶庫會顯示「(主持人未寫結論)」。
- `## 第 N 輪`:依序列出每一輪。
- `### 名稱 · 節點ID`:每則發言一個標題;沒有 ID 的發言者寫成 `### 主控台 · -`。
- 每則發言和結語都**逐行加上 `> `**,空行也要寫成 `>`。
  - 這樣發言內容裡的標題、程式碼區塊、表格都在引用區塊裡，不會打亂結構。
  - 寶庫只剝掉外加的那一層。
  - 不採「把內文標題降級」的做法，因為降級後還是可能和發言者標題撞在一起。

### 4. 可見性
- `memory_search`、`memory_read` 和 `[[...]]` 的解析，對節點只提供「已確認」的會議紀錄。就算節點知道檔案路徑，也要檢查狀態。
- 確認會議紀錄，不會連帶確認它產出的決策，兩者各自確認。

### 5. 熱度
會議紀錄被 `memory_read` 讀取時，照樣計入 `.nexus-heat.json`。

### 6. 隱私
寫入時遮罩金鑰，沿用 maskSecrets。另外按欄位處理本機路徑:
- **可見文字**(主題、摘要、結語、逐字稿):本機絕對路徑整段換成「[本機路徑已隱藏]」。涵蓋的寫法有 `X:\` 和 `X:/`、`file:///`、UNC、`/Users/…`、`/home/…`。相對路徑保留。
  - 不採用「把家目錄換成 `~\`」的做法，因為只換前綴，還是會留下私人資料夾的名稱。
- **結構欄位** `專案ID`:原樣保留，供內部分組。`memory_read` 回傳的檔頭要不要隱藏專案ID,和判例一起另外再議。
- 寶庫畫面本身另有更嚴格的遮罩，兩邊各自負責，不必一致。

### 7. 寶庫 App(vault keeper 負責)
- **第五個書架「會議紀錄」**:不放進典藏書架。
- **卡片外型「頂緣線圈裝訂」**:上緣置中 5 個凸出紙緣的金色小圓環，加一道細縫線，和判例、決策、書籤、典藏四種外型都分得開。
  - 另外有參與者小圓點，以及中止或逾時的小標籤。
  - 正式設計稿由 Hagemi 出。
- **識別碼**:「會議 · 日期」,不編號。
- **待核閱案頭**:會議另外計數，例如「待核閱 N · 未完書籤 M · 會議 K」。
- **閱讀桌的會議檢視**:結論置頂、各輪目錄、依輪次摺疊、可以篩選發言者；發言者要寫出名字，不能只靠顏色區分。
- **里程碑**:M6a 做資料、書架和確認流程;M6b 做閱讀體驗、決策雙向跳轉，以及同席連線連到會議紀錄。

### 8. 使用者裁示(2026-11-22,照建議)
1. **退回**:檔案保留、節點查不到，在寶庫顯示「已退回」,之後還可以再確認。要刪除就用既有的「移入回收」。
2. **批次確認**:第一版不做。實際累積量大了以後，再在案頭的會議計數旁加一個「全部確認」按鈕，按下前先跳確認視窗。

## 第六輪:回憶錄(2026-11-23,Hagemi 召開的短會,使用者裁示)

**使用者已決定**:
- 記憶庫新增「回憶錄」:節點用第一人稱回顧自己的經歷(做過什麼、怎麼想、和使用者或其他節點怎麼合作、學到什麼、哪裡做得不好),一章一個檔案。
- 和記憶草稿、判例一樣,先由主控台發出請求,節點才能提交;寫進去是「未確認」,使用者確認後節點才查得到。
- 使用者裁示這件事插隊先做。

### 1. 路徑
`memoirs/<節點名>-<節點ID 前 8 碼>/<YYYY-MM-DD>-<標題>.md`
- 日期是寫入當天的本機日期。
- 節點名與標題沿用會議紀錄的檔名規則:`safeName`,另外去掉 `[ ] # ^ |`;資料夾開頭的 `_` 和 `.` 也去掉(記憶庫不掃描那種資料夾)。全部被去掉時寫「未命名」。
- 標題先遮罩本機路徑與金鑰,再轉成檔名。
- 同名時加 `-2`、`-3`,不覆蓋舊檔。
- 每個節點一個資料夾,用 ID 前 8 碼區分同名節點;節點改名後新的章節會在新名稱的資料夾。寶庫比對節點時要以檔頭的 `節點ID` 為準,不要只看資料夾名稱。

### 2. 檔頭欄位
只放單行欄位,字串值一律用雙引號(跳脫 `\` 和 `"`,和會議紀錄相同),依序是:

| 欄位 | 內容 |
|---|---|
| `種類` | `回憶錄`(索引的 kind 是 `memoir`) |
| `節點ID` | 提交者的節點 ID,**主控台填** |
| `節點` | 提交者的名稱,**主控台填** |
| `後台` | 提交者的後台名稱(例如 Claude Code),**主控台填** |
| `標題` | 這一章的標題(遮罩後) |
| `涵蓋期間` | ISO 日期區間 `YYYY-MM-DD/YYYY-MM-DD`,只有一天可只寫起日 `YYYY-MM-DD` |
| `範圍` | 一律 `全域`(回憶錄沒有專案) |
| `更新時間` | 寫入時間,本機時間 `YYYY-MM-DD HH:mm:ss` |
| `狀態` | `未確認` |

節點在參數裡填的 `節點ID`、`節點`、`後台`(以及狀態、範圍等)一律忽略;一個節點不能替別的節點寫回憶錄。去識別樣本:`docs/memory-vault-app/回憶錄樣本.md`(由 `tools/make-memoir-sample.mjs` 用實際的組成程式產生)。

### 3. 正文固定章節
- 正文開頭是自由的回憶內容(Markdown)。
- 必須有 `## 來源`(這一章根據什麼寫的:哪段對話、哪些任務、哪些記憶或檔案)與 `## 不確定之處`(記不清楚、推測的地方)兩個二級標題章節,順序不限。
- 章節內容可以只寫「無」,但章節不能缺,也不能是空的(只有空白或 HTML 註解也算空);缺了或空的就拒收,錯誤訊息請節點補上後重寫。
- 標題的認法依 CommonMark 的 ATX 標題(前面 0 到 3 個空白、結尾可以有一串 `#`),另外接受標題名後的冒號(半形、全形)與包在粗體裡的寫法;程式碼圍欄依 CommonMark 配對(``` 只能由至少一樣長的 ``` 關閉,`~~~` 同理),圍欄與 HTML 註解裡的 `## ` 不算。
- 標題去掉不可見的格式字元(零寬字元、U+202E 等),依字元截斷不切開代理對;檔名同樣處理。
- 正文超過 12000 字直接拒收(不截斷,免得剛好切掉固定章節)。提示詞請節點控制在 2000 字內。

### 4. 可見性
- 比照判例與會議紀錄:只有 `狀態: 已確認` 的回憶錄對節點可見(`memory_search` 的 kind `memoir`,以及 `memory_read`,含直接給路徑)。未確認與退回的都看不到,寫的節點自己也一樣。
- 範圍是全域,確認後任何專案的節點都查得到。

### 5. 提交規則
- 節點用既有的 `memory_draft` 工具提交,`kind` 填 `memoir`(別名「回憶錄」),另有 `period`(涵蓋期間)參數;`title`、`content` 和記憶草稿相同。
- **必須先由主控台發出請求**,而且只有被請求的節點、一次請求一份。回憶錄請求和一般記憶草稿請求分開記:提示詞專門寫給回憶錄,兩種請求互不通用(拿回憶錄請求交 knowledge 會被擋,反之亦然)。舊請求還在進行(提示還在佇列,或節點正在跑回憶錄的回合)時不能重複請求;請求掛著但已經不在進行(例如上一份不合格後節點就停了),可以重新請求,覆蓋舊請求。
- 格式不合格(缺章節、涵蓋期間格式不對、日期不存在、起日晚於迄日)拒收,但請求保留,節點可以補上重寫。
- **每個節點每天最多 3 份**(本機日期;請求時與提交時都檢查,比照判例的每日上限做法)。
- 寫入時遮罩金鑰(`maskSecrets`)與本機絕對路徑(`maskLocalPaths`,換成「[本機路徑已隱藏]」),範圍是標題與正文。
- `memory_write` 不能寫回憶錄(總管也不行),比照會議紀錄的拒絕。

### 6. 觸發入口
- **對話視窗**:「寫回憶錄」按鈕和「儲存這段記憶」並列。回憶錄不看累積字數,最上層的對話模式節點都有這個按鈕;子代理與終端機模式不提供,節點休眠或失聯時按鈕停用。
- **刪除節點**:現在的歸檔流程先問要不要請節點寫工作總結;選好之後再問一次要不要寫回憶錄(節點離線或在終端機模式時寫不了,不問)。選「寫回憶錄再刪除」時,主控台先送出「最後一章」的回憶錄請求,等節點提交(或這個回合結束、逾時 3 分鐘),再照原本的流程寫總結、歸檔、刪除;如果使用者先按過「寫回憶錄」、那份請求還在佇列或節點正在寫,就不重發,等那一份寫完。逾時時取消請求、拿掉佇列裡的回憶錄提示、中斷正在寫的回合;沒寫成不擋刪除,結果寫在歸檔說明裡。異常狀態的節點不問。刪除等待期間,「寫回憶錄」與「儲存這段記憶」停用。
- **不做**:定時喚起節點寫回憶錄;`entropy-nexus://memoir` 協定。

### 7. 和寶庫的分工
- 主控台負責:請求、驗證、寫檔、索引、可見性;不提供瀏覽或確認回憶錄的畫面。
- 寶庫負責:瀏覽、閱讀、確認或退回(改 `狀態`)。
- **寶庫的書架定位(獨立書架、併入既有書架或其他呈現方式)另待使用者裁示**,主控台這邊的格式不受影響。寶庫要能處理只有起日的 `涵蓋期間`。

以下是討論時的原始資料。

---

## 一、記憶要解決什麼

總管分派工作時,現在只看得到 `list_nodes` 給的資訊(名稱、後台、模型、狀態、工作目錄)。它不知道:

- 哪個節點擅長什麼、最近表現如何(例如「Hagemi 查資料快,寫程式比較粗」)
- 這個專案的慣例(例如「這個 repo 改 UI 要跑 `tests/layout.sh`」)
- 你的偏好(例如「回報要精簡」「commit 前要先問」)
- 過去類似的工作交給誰、結果如何

各家 CLI 有各自的記憶(Claude 的 CLAUDE.md 與 memory、Codex、Gemini 各自的設定),但彼此不相通,也不知道其他節點存在。主控台是唯一看得到所有節點與所有結果的地方。

---

## 二、記憶的種類

| 種類 | 例子 | 誰產生 | 天生的範圍 |
|---|---|---|---|
| **節點側寫** | 「Hagemi:擅長網路查證、整理成表格;寫程式時常漏邊界條件」 | 總管寫(已決定) | 跟著節點走 |
| **自動統計** | 每個節點的完成率、平均耗時、花費、被打回的次數 | 主控台自動算,不用 agent 寫 | 跟著節點走,可依專案細分 |
| **專案知識** | 「改 UI 要跑版面檢查」「測試要先 build」 | 總管(之後也許其他節點)寫 | 依專案 |
| **使用者偏好** | 「回報精簡」「不要自動推送」 | 總管寫,或你直接寫 | 全域 |
| **分派紀錄** | 「11/20 把 ElevenLabs 研究交給 Hagemi,結果完整」 | 主控台自動記 | 依專案 |

注意「節點」本身就是全域的:同一個 Hagemi 可能在好幾個專案工作。

---

## 三、範圍的三個方案

### 方案 A:全部全域共用

所有記憶放在一起,總管隨時都看得到全部。

- 優點:最簡單;節點側寫天生就是全域的。
- 缺點:專案知識會互相混淆,例如 A 專案的「測試要先 build」被套到 B 專案;專案越多越雜,總管要讀的內容越長。

### 方案 B:全部依專案分開

每個專案一份記憶,互不相通。

- 優點:乾淨,不會混淆。
- 缺點:節點側寫和你的偏好要在每個專案重寫一次;新專案一開始什麼都不知道。

### 方案 C:混合式(建議)

同一張資料表,每筆記憶有一個「範圍」欄位:`全域` 或 `專案:<識別>`。

- 節點側寫、使用者偏好 → **全域**
- 專案知識、分派紀錄 → **專案**
- 自動統計 → 全域彙總,另外可以依專案細分(例如「Hagemi 在這個 repo 的完成率」)
- 總管查詢時,同時拿到「全域 + 目前專案」的記憶。

優點:兩邊的好處都有;之後想改成純 A 或純 B,只是查詢條件不同,不用搬資料。
缺點:寫入時要判斷範圍,總管可能放錯。可以讓預設值依種類決定,減少判斷。

---

## 四、「專案」怎麼認定

| 方式 | 說明 | 問題 |
|---|---|---|
| 節點的工作目錄 | 最簡單 | 同一個 repo 的不同 worktree(例如獨立工作區)會被當成不同專案 |
| git repo 的根目錄(`--show-toplevel`) | | worktree 的根目錄也各自不同,同樣的問題 |
| **git 的共用目錄(`--git-common-dir`)**(建議) | 同一個 repo 的所有 worktree 會得到同一個值 | 不是 git repo 的資料夾,改用工作目錄 |

建議:是 git repo 就用 `--git-common-dir` 對應到主 repo 的路徑;不是 git repo 就用工作目錄本身。畫面上顯示成資料夾名稱,例如「entropy nexus public」。

另一個問題:**總管本身在哪個專案?** 總管的工作目錄不一定是它分派的那個專案。建議查詢「目前專案」時,用**被交辦節點的工作目錄**判斷,而不是總管自己的;總管寫入專案知識時要指定是哪個專案(可以用節點名稱或資料夾)。

---

## 五、誰能寫、寫什麼

| 選項 | 說明 |
|---|---|
| 只有總管能寫(第一階段建議) | 記憶來源單一,比較不會變雜;內容先限定節點側寫 |
| 總管寫全部種類,其他節點只能讀 | 第二階段 |
| 所有節點都能寫專案知識 | 最彈性,但容易重複、互相矛盾,需要整理機制 |
| 你可以直接在畫面上新增、編輯、刪除 | 不論哪個選項都建議有 |

每筆記憶都記下來源(哪個節點、什麼時候、哪個任務),畫面上看得到。

---

## 六、總管怎麼用到記憶

1. **自動附上**:總管的身分設定(現在的「總管守則」)後面附一段精簡的節點側寫,例如每個節點一行:特長 + 最近 20 個任務的完成率。限制長度,例如 1500 字以內。
2. **主動查詢**:MCP 工具 `memory_search(關鍵字, 範圍)`,需要時再查專案知識或分派紀錄。
3. **寫入**:MCP 工具 `memory_write(種類, 內容, 範圍)`;第一階段只開放總管寫節點側寫。

自動附上的內容會在每次總管守則更新時重送,所以要短;詳細的靠查詢。

---

## 七、自動統計:目前已經有的資料

儀表做完後,資料庫已經有:

- `tasks`:每個任務的節點、狀態(完成、失敗、中斷)、開始與結束時間、花費、來源(桌面、遠端、節點互相呼叫、總管)。
- `task_daily`:每天的任務統計(清除任務面板後仍保留)。
- `spend_daily`:每天、每個節點的 token 與金額。

所以「完成率、平均耗時、花費」可以直接算出來,不需要新的收集機制。缺的是:

- **被審查的結果**(例如審查節點提了幾個問題)— 目前沒有結構化資料。
- **任務屬於哪個專案** — 要加上專案識別(第四節)。

---

## 八、隱私與注意事項

- **記憶會送給其他廠商的模型。** 總管是 Gemini 時,節點側寫和你的偏好會送到 Google;總管是 Codex 時送到 OpenAI。這和現在的節點互相呼叫一樣,但記憶是長期累積的,內容可能更多。建議在畫面上說明,並讓你可以把某些記憶標成「不提供給 agent」。
- 記憶裡不要存密碼、金鑰。寫入時可以做簡單的檢查(看起來像金鑰的字串就拒絕)。
- 遠端裝置:檢視記憶要完整權限。

---

## 九、保存與整理

- 節點側寫:同一個節點只保留一份,總管更新時覆寫(保留修改紀錄)。
- 專案知識:可能越來越多。選項:設上限(例如每個專案 50 筆)、保存期限、或定期請總管整理合併。
- 節點被刪除時:側寫保留(之後同名節點可以接回)還是一起刪?

---

## 十、要決定的問題

1. **範圍**:A 全域、B 依專案、C 混合式(建議 C)?
2. **專案認定**:用 git 共用目錄、非 git 用工作目錄(建議)?
3. **第一階段誰能寫**:只有總管、只寫節點側寫(已決定的範圍)?之後要不要開放專案知識給總管、給其他節點?
4. **自動附給總管的內容**:節點側寫 + 完成率,限制 1500 字左右,可以嗎?
5. **隱私**:要不要「不提供給 agent」的標記?記憶管理只給桌面與完整權限的遠端?
6. **整理方式**:專案知識要設上限、期限,還是定期整理?
7. **節點刪除時**:側寫保留還是刪除?

---

## 建議的分階段

1. 資料表(含範圍欄位)、專案識別、自動統計;總管守則附上節點統計(還沒有側寫)。
2. `memory_write`(總管寫節點側寫)、`memory_search`;總管守則附上側寫。
3. 記憶管理畫面(檢視、編輯、刪除、標記)。
4. 視第三點的決定,開放專案知識與分派紀錄。
